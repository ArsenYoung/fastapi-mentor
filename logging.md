# Logging Guide

Этот документ объясняет, **какой подход к логированию выбрать в проекте FastAPI**, зачем нужен `request_id`, как не утонуть в шуме и как сделать логи полезными для отладки.

Я пишу это "для чайника", то есть без лишней теории, но с понятными примерами.

---

## 1. Зачем вообще нужны логи

Логи нужны, чтобы потом ответить на простые вопросы:

- что произошло?
- где именно произошло?
- с каким запросом это связано?
- сколько заняло по времени?
- почему пользователь получил ошибку?

Без логов ошибка выглядит так:

```text
что-то сломалось
```

С логами ошибка выглядит так:

```text
request_id=7f4e... method=GET path=/students/15 status=404 message="Student not found" student_id=15
```

Второй вариант уже помогает найти причину, а не просто факт поломки.

---

## 2. Какой подход выбрать

### Рекомендация для этого проекта

Для этого проекта лучше выбрать **structured logging**:

- логировать не обычный текст, а поля;
- хранить события в JSON;
- добавлять `request_id` к каждому запросу;
- прокидывать контекст автоматически через `contextvars`.

### Почему именно так

- это удобно читать глазами;
- это удобно искать через `grep`, Kibana, Loki, Graylog и аналоги;
- это хорошо работает в `asyncio` и FastAPI;
- это проще поддерживать, чем ручные `print()` и строковые сообщения;
- это можно делать без огромной инфраструктуры.

### Что я рекомендую конкретно

Для небольшого FastAPI-проекта лучший баланс такой:

- использовать `structlog` или аналогичный structured logging;
- хранить контекст запроса в `contextvars`;
- генерировать `request_id` в middleware;
- возвращать `X-Request-ID` в ответе;
- логировать ошибки один раз, на границе приложения.

Если хочется совсем минимально зависеть от внешних библиотек, можно сделать и на стандартном `logging`. Но для этого проекта structured logging понятнее и полезнее.

## 3. Что такое `request_id`

`request_id` - это уникальный номер конкретного HTTP-запроса.

Можно думать о нем как о талоне в очереди:

- каждый запрос получает свой номер;
- все события внутри этого запроса помечаются этим номером;
- потом по этому номеру легко собрать всю историю запроса.

### Зачем он нужен

Без `request_id` логи от разных запросов смешиваются:

```text
request 1 started
request 2 started
request 1 failed
request 2 finished
```

Если запросов много, глазами это уже сложно разобрать.

С `request_id` все становится связано:

```text
request_id=a1 started
request_id=b2 started
request_id=a1 failed
request_id=b2 finished
```

Теперь можно быстро собрать всё, что относилось именно к одному запросу.

## 4. Почему нужен `contextvars`

FastAPI работает асинхронно. Это значит, что в одном потоке могут одновременно жить несколько запросов.

Если использовать старый подход вроде `thread-local`, данные могут смешиваться.

`contextvars` решает эту проблему:

- сохраняет данные в контексте текущего async-запроса;
- не требует передавать `request_id` через каждую функцию руками;
- работает естественно для `asyncio`.

То есть идея такая:

- middleware кладет `request_id` в `contextvars`;
- дальше любой лог в этом запросе сам получает этот `request_id`;
- ничего вручную протаскивать не нужно.

## 5. Что именно логировать

### Логировать стоит

- начало запроса;
- завершение запроса;
- время выполнения;
- статус ответа;
- ожидаемые бизнес-ошибки;
- неожиданные ошибки;
- вызовы внешних сервисов, если они появятся позже;
- важные бизнес-события, например создание студента или автора.

### Логировать не стоит

- пароли;
- токены;
- cookies;
- authorization header;
- полный request body без маскирования;
- слишком много одинаковых успешных SQL-запросов;
- один и тот же exception в нескольких слоях подряд.

### Простое правило

Если лог не поможет потом понять проблему, он, скорее всего, лишний.

---

## 6. В каких местах логировать

### Router

Роутер почти не должен заниматься логированием.

Его задача:

- принять запрос;
- вызвать сервис;
- вернуть ответ.

Если логировать слишком много в роутере, получится шум.

### Service

Сервис - хорошее место для логов бизнес-событий.

Например:

- студент создан;
- автор не найден;
- курс уже существует;
- запрос на обновление данных принят.

Сервис понимает смысл операции, поэтому лог в сервисе обычно полезнее, чем в репозитории.

### Repository

Репозиторий не должен быть болтливым.

Его задача:

- читать и писать данные;
- не превращаться в журнал каждого SQL-запроса.

Логировать каждую строку SQL почти всегда плохая идея: будет шум, а пользы мало.

### Middleware

Middleware - лучшее место для:

- генерации `request_id`;
- замера времени запроса;
- логирования начала и конца запроса;
- добавления `X-Request-ID` в ответ.

### Exception handlers

Обработчики исключений нужны, чтобы:

- вернуть нормальный HTTP-ответ;
- записать ошибку в лог;
- не дублировать обработку ошибок в каждом endpoint.

## 7. Как должен выглядеть хороший лог

Хороший лог - это не длинный абзац текста, а набор полей.

### Пример хорошего события

```json
{
  "event": "request_finished",
  "request_id": "7f4e2c6d",
  "method": "GET",
  "path": "/students/15",
  "status_code": 404,
  "duration_ms": 12,
  "level": "warning",
  "message": "Student not found"
}
```

### Почему это хорошо

- сразу видно, что случилось;
- легко искать по `request_id`;
- легко фильтровать по `status_code`;
- легко искать медленные запросы;
- удобно строить графики и алерты.

### Плохой пример

```text
oops something went wrong in students endpoint
```

Почему плохо:

- непонятно, какой это запрос;
- непонятно, какой статус;
- непонятно, какой объект;
- непонятно, сколько длилось;
- непонятно, можно ли это воспроизвести.

---

## 8. Какой формат сообщений выбрать

### Для имени события

Используй короткие английские идентификаторы в стиле `snake_case`:

- `request_started`
- `request_finished`
- `student_created`
- `student_not_found`
- `course_conflict`
- `unexpected_error`

### Для текста сообщения

Сообщение должно быть коротким и понятным:

- `Student not found`
- `A student with this record book number already exists`
- `Unexpected error`

### Хорошее правило

- `event` - короткий машинный идентификатор;
- `message` - короткий человеческий текст;
- `details` - дополнительный контекст, например id объекта.

---

## 9. Как использовать `details`

`details` нужен для дополнительного контекста.

### Пример

```python
raise ObjectNotFoundException(
    "Book not found",
    details={"book_id": 15}
)
```

Тогда клиент и лог увидят не просто "книга не найдена", а еще и конкретный `book_id`.

### Когда это особенно полезно

- когда не найден объект;
- когда есть конфликт уникальности;
- когда нужна диагностика по конкретному id;
- когда ошибка повторяется и нужен контекст для анализа.

### Что лучше хранить в `details`

- `book_id`
- `student_id`
- `author_id`
- `passport_number`
- имя поля, которое сломалось

### Что не стоит класть в `details`

- пароли;
- токены;
- полные персональные данные;
- cookies;
- большие куски тела запроса без необходимости.

---

## 10. Как это выглядит в FastAPI

### Общая схема

1. приходит HTTP-запрос;
2. middleware назначает `request_id`;
3. middleware кладет `request_id` в `contextvars`;
4. сервис или роутер делает работу;
5. если все хорошо - пишется лог завершения;
6. если ошибка - exception handler пишет лог ошибки;
7. клиент получает ответ с `X-Request-ID`.

### Пример логической последовательности

```text
request_started
student_not_found
request_finished
```

или

```text
request_started
student_created
request_finished
```

или при ошибке:

```text
request_started
unexpected_error
request_failed
```

## 11. Что делать с ошибками

### Главное правило

Ошибку нужно не только показать клиенту, но и записать в лог.

### Что должно быть в сообщении об ошибке

- что случилось;
- с каким объектом;
- на каком endpoint;
- какой `request_id`;
- если это 500, то stack trace.

### Как логировать разные ошибки

#### 404 / object not found

Это обычно ожидаемая ситуация, а не авария.

Логировать можно как `warning`.

Пример:

```json
{
  "event": "student_not_found",
  "request_id": "7f4e2c6d",
  "student_id": 15,
  "level": "warning"
}
```

#### 409 / conflict

Тоже часто ожидаемая бизнес-ситуация.

Логировать можно как `warning`.

Пример:

```json
{
  "event": "student_conflict",
  "request_id": "7f4e2c6d",
  "record_book_number": "212866",
  "level": "warning"
}
```

#### 500 / unexpected error

Это уже реальная проблема системы.

Тут нужен `error` и stack trace.

Пример:

```json
{
  "event": "unexpected_error",
  "request_id": "7f4e2c6d",
  "exception": "IntegrityError",
  "message": "Unexpected error",
  "level": "error"
}
```

---

## 12. Где ошибка должна логироваться один раз

Очень важное правило: **не логируй одну и ту же ошибку в трех местах**.

### Плохой вариант

- repository пишет ошибку;
- service пишет ту же ошибку;
- exception handler пишет ту же ошибку еще раз.

В итоге в логах дубли и шум.

### Хороший вариант

- repository просто делает запрос;
- service решает, что это за ситуация;
- exception handler или middleware пишет итоговый лог один раз.

Так проще искать причины и меньше мусора.

---

## 13. Что делать с успешными запросами

Не только ошибки полезно логировать.

### Полезно логировать

- старт запроса;
- завершение запроса;
- `status_code`;
- `duration_ms`;
- ключевые бизнес-события.

### Не обязательно логировать

- каждую успешно прочитанную строку из БД;
- каждый внутренний шаг без ценности;
- каждый вызов вспомогательной функции.

### Простое правило

Если лог нельзя использовать для отладки или анализа, он, скорее всего, лишний.

---

## 14. Что выбрать: файл, stdout или база

### Для этого проекта

Лучше всего начинать с:

- вывода в stdout;
- JSON-формата;
- потом уже при необходимости подключать сборщик логов.

### Почему не база сразу

Хранить логи сразу в базе можно, но для маленького проекта это обычно лишнее:

- сложнее поддерживать;
- больше кода;
- нет реальной пользы на старте.

### Когда база или отдельный лог-хранилище уже нужны

- когда много сервисов;
- когда много трафика;
- когда нужен поиск по огромной истории;
- когда есть отдельная observability-инфраструктура.

Для текущего проекта этого не требуется.

---

## 15. Что делать с `request_id` между сервисами

Сейчас проект один.

Но если позже появятся внешние сервисы, нужно:

- принимать `X-Request-ID` от клиента;
- если его нет, создавать новый;
- передавать его дальше во внешние запросы;
- писать его в каждый лог.

Это позволит смотреть один и тот же запрос через несколько систем.

## 16. Пошаговый план для этого проекта

### Шаг 1. Выбрать формат логов

Я рекомендую:

- structured logging;
- JSON;
- английские `event` и `message`;
- `request_id` в каждом событии.

### Шаг 2. Добавить `request_id` middleware

Middleware должен:

- прочитать `X-Request-ID` из входящего запроса;
- если заголовка нет, сгенерировать UUID;
- положить `request_id` в `contextvars`;
- добавить `X-Request-ID` в ответ;
- замерить `duration_ms`.

### Шаг 3. Настроить logger

Нужно, чтобы лог автоматически добавлял:

- `request_id`;
- `method`;
- `path`;
- `level`;
- `timestamp`.

### Шаг 4. Добавить логирование ошибок

В exception handlers нужно:

- логировать `404` и `409` как `warning`;
- логировать неожиданные ошибки как `error`;
- возвращать клиенту нормальный JSON-ответ.

### Шаг 5. Добавить несколько бизнес-логов

Например:

- `student_created`;
- `author_created`;
- `person_created`;
- `student_not_found`.

### Шаг 6. Не переборщить

Не нужно логировать каждую строчку кода.

Логи должны помогать, а не мешать.

## 17. Какие файлы лучше добавить позже

Когда дойдёшь до реализации, я бы советовал такие файлы:

- `src/middleware/request_id.py`
- `src/core/logging_config.py`
- `src/core/logging_context.py`

Важно: **не называй модуль `logging.py`**, потому что это легко перепутать со стандартной библиотекой Python.

## 19. Типичные ошибки новичков

### Ошибка 1. Использовать `print()`

`print()` быстро кажется удобным, но потом:

- сложно искать;
- сложно фильтровать;
- сложно собирать;
- сложно анализировать.

### Ошибка 2. Логировать слишком много

Если логировать все подряд, нужные записи потеряются в шуме.

### Ошибка 3. Логировать одинаковую ошибку в трех слоях

Одна ошибка должна появиться в логах один раз, а не три.

### Ошибка 4. Не передавать `request_id`

Без `request_id` логи теряют связь друг с другом.

### Ошибка 5. Логировать чувствительные данные

Это опасно.

Нельзя писать в лог:

- пароли;
- токены;
- cookies;
- секреты;
- полный payload без маскирования.

---

## 20. Короткий итог

Для этого проекта лучший подход такой:

- structured logging;
- `request_id` для каждого запроса;
- `contextvars` для хранения контекста;
- JSON-логи;
- ошибки логируются на границе приложения;
- бизнес-события логируются в сервисах;
- репозитории остаются максимально тихими;
- чувствительные данные в лог не пишем.

Если совсем коротко:

- **request_id** нужен, чтобы связать все записи одного запроса;
- **structured logging** нужен, чтобы логи можно было нормально искать и анализировать;
- **contextvars** нужны, чтобы это работало правильно в async FastAPI.
